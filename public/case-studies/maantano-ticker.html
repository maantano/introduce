Problem

차트 앱을 켜는 게 귀찮아서, 메뉴바를 봤다

평소에 주식을 자주 들여다보지는 않지만 시장에 큰 변동이 있을 때만 빠르게 확인하고 싶었다. 매번 브라우저나 증권 앱을 켜는 흐름은 끊김이 크고, 메뉴바에는 마침 비어 있는 공간이 있었다. 이미 시중에 비슷한 앱이 있지만 — 한국 주식 미지원, 한국식 적/청 컬러 미적용, 텍스트 색·크기 조절 불가 — 내 사용 흐름에 맞지 않았다.

⏱️

흐름이 끊긴다

관심 종목을 잠깐 보기 위해 브라우저/앱을 열고 로그인까지 가는 비용이 너무 컸다.

🌏

국내·해외 분리

한국 주식과 미국 주식을 함께 트래킹하려면 결국 두 곳을 동시에 봐야 했다.

🎨

가독성

메뉴바는 좁고 OS 테마에 따라 색이 묻힌다. 한국식 적/청 관습도 맞춰야 했다.

Solution

항상 보이는 미니 시세 + 클릭 한 번에 다종목 관리

트레이 아이콘 자리에 첫 번째 관심 종목의 이름·가격·등락률을 작게 그려 상시 노출하고, 클릭하면 360px 폭의 작은 팝업으로 다종목 리스트·검색·드래그 재정렬·설정을 제공. 한·미 시장은 탭으로 분리하지만 시세 표시는 동일한 흐름으로 일관되게 처리.

Key Decisions

설계에서 신경 쓴 4가지

01 메뉴바 텍스트는 직접 그린다

왜
macOS 기본 트레이 타이틀은 색·자간·다국어 처리에 제약이 있었다. 상승 빨강 / 하락 파랑(한국식)처럼 부분 컬러링이 핵심 요구였기 때문에 텍스트를 이미지로 렌더링하는 길을 선택.
어떻게
Node canvas로 Retina 스케일을 고려해 @2x 비트맵을 생성하고 트레이 이미지로 주입. 색·크기는 사용자 설정에 따라 매 갱신마다 다시 그림.

02 시장은 Factory로 분리한다

왜
한국과 미국은 데이터 소스, 통화, 표기, 거래 시간이 완전히 다르다. 처음부터 if-else로 묶으면 시장 추가 시 분기가 폭발한다.
어떻게
`StockServiceFactory`가 시장 키로 서비스 인스턴스를 반환하고, Renderer는 단일 facade(`StockDataManager`)만 호출. 다종목 갱신 시에는 시장별로 묶어 병렬 처리해 응답 지연을 줄였다.

03 장 마감이면 호출하지 않는다

왜
5초 간격으로 무조건 호출하면 야간·주말에도 트래픽이 발생하고, 종목 수가 늘수록 외부 API 부하가 커진다.
어떻게
한국은 KST 기준 정규장+시간외 구간을, 미국은 EST/EDT 서머타임 자동 계산 후 정규장 구간을 게이트로 적용. 거래 시간 밖에서는 갱신을 건너뛰고 마지막 값을 그대로 유지.

04 죽은 종목은 알아서 빠진다

왜
상장폐지·합병으로 종목 코드가 사라지면 사용자는 영문도 모르고 계속 에러를 본다.
어떻게
종목 객체에 연속 실패 카운터를 두고, 임계치를 넘은 종목을 종목 DB와 교차 확인. 둘 다 음성이면 목록에서 자동 제거하고 사용자에게 시스템 다이얼로그로 안내.

Architecture

3-레이어로 단순하게

Electron의 두 프로세스를 UI 책임(Renderer)과 OS 통합 책임(Main)으로 나누고, 그 사이에 Service 레이어를 두어 외부 데이터 소스와 UI를 격리. 데이터 소스가 바뀌어도 UI는 영향을 받지 않는 구조.

UI는 facade 하나만 알고, facade가 시장별 provider에게 위임. OS 통합은 Main 프로세스에 격리.

Tech Stack

가능한 한 가볍게

개인 데스크톱 앱이라 번들 크기와 메모리를 의식했고, 프레임워크보다 vanilla JS로 직접 다루는 쪽을 택했다. 복잡도를 늘리지 않고도 충분히 관리 가능한 규모로 유지하는 것이 목표.

Runtime
  • Electron 28 데스크톱 셸

  • Vanilla JS 프레임워크 없음

Reflection

이 프로젝트에서 배운 것

OS 통합은 "보이지 않게 정확히" 가 핵심이다

메뉴바 아이콘은 한 번 거슬리기 시작하면 바로 지워진다. 폰트 크기, 자간, 다크모드 색상 대비, 텍스트 잘림 — 사용자가 의식하지 않는 디테일이 채택률을 결정한다. 작은 캔버스 렌더링 하나에 가장 많은 시간을 썼다.

혼자 만드는 앱일수록 배포가 제품의 일부다

"빌드 후 DMG를 어디서 받는지" 한 단계만 막혀도 사용자는 떠난다. 자동 버전 관리와 Homebrew Cask 자동화는 처음에는 과해 보였지만, 결과적으로 업데이트 사이클을 짧게 유지하는 가장 큰 이유가 됐다.

외부 데이터를 다룰 때는 "예의"가 필요하다

공개된 데이터라도 호출 간격을 두고, 거래 시간 밖에서는 호출하지 않고, 사용 목적과 면책 사항을 README에 명시하는 식의 운영 기본기. 기능을 만드는 것보다 지속 가능하게 운영하는 감각이 더 중요하다는 걸 체감했다.

다음 버전이라면

차트 미니뷰, 알림(임계치 도달 시 푸시), 환율 자동 환산, 그리고 Apple Notarization을 통한 정식 서명까지 — 사용자 신뢰를 한 번 더 올릴 수 있는 단계가 명확히 보인다.
