200+ 채널의 하루를, 매일 아침 한 통의 요약으로

팀 메신저 채널이 늘어나면서 “어제 무슨 일이 있었는지”를 사람이 따라가 읽는 것이 비현실적이 됨. 이 봇은 평일 아침마다 모든 공개 채널의 24시간 대화를 자동 수집해 LLM 2-stage 파이프라인으로 카테고리별 요약을 만들고, 한 채널에 일일 다이제스트로 발송합니다. 신뢰성과 비용을 모두 잡기 위해 결정적 fallback, chunk 단위 멱등 회복, hang 가드를 직접 설계했습니다.

01문제와 결과

풀고 싶었던 문제

  • 채널이 수백 개 단위로 늘어나면서 구성원이 “어제 회사에서 무슨 일이 있었는지”를 따라잡을 수 없게 됨.
  • 중요한 의사결정·일정·외부 자료가 채널 단위로 흩어져 사장됨.
  • 사람이 매일 직접 요약하기에는 시간/일관성이 모두 부족.

요구 조건

  • 한 통의 메시지로 끝나야 함 — 그 자체가 “받아 읽는” 단위.
  • 발송이 단 하루도 누락되면 신뢰가 깨짐. 실패해도 어떤 형태로든 한 줄은 도착해야 함.
  • 같은 입력에는 같은 결과가 나와야 디버깅이 가능.

결과

  • 출시 후 발송 누락 0건. LLM 실패·네트워크 hang·메시지 분할 도중 throw 등 6종류의 사고를 설계 단계에서 차단.
  • 새 공개 채널은 사람 개입 없이 다음 발사부터 자동 흡수.
  • 한 회차 평균 처리 시간 ~5분 — cron 한 번이 수집·요약·합성·발송을 모두 마침.
  • 토픽이 하나도 없는 조용한 날도 “조용한 하루였습니다” 한 줄 안내로 봇 생존 신호 제공.

비고

  • 이 문서는 구조·의사결정만 다룹니다. 도메인 키워드·내부 상수·식별자는 일반화했습니다.

03파이프라인 설계

cron 트리거 한 번이 6단계를 순차 실행합니다. 각 단계는 자체 timeout · 재시도 · 폴백을 가져 한 단계가 죽어도 다음 단계가 진행됩니다.

왜 2-stage인가

  • 비용 — 채널 200개 분량의 raw 메시지를 한 번에 한 모델에 통째로 넣으면 컨텍스트가 폭증. 채널별로 작은 LLM 호출을 병렬로 돌리고, 합성만 한 번 더 큰 호출로 처리하는 게 토큰/비용 면에서 압도적으로 유리.
  • 안정성 — Stage 2가 실패해도 Stage 1까지의 구조화 결과는 살아 있음. 그 위에서 결정적 fallback이 “최소 뉴스레터”를 보장.
  • 품질 — 채널 문맥(채널명·운영 목적)을 작은 호출에 주입하고, 합성 단계는 “보존·정렬·그룹핑”에 집중하도록 책임 분리.

04기술적 의사결정

D1상태를 메시지 채널에 위임

별도 DB를 두지 않고 “출력 채널 자체”를 단일 진실 소스로 삼았습니다. 어떤 인스턴스가 떠 있든, 어디서 죽었든, 같은 채널을 읽으면 다음 행동이 결정됩니다.

Problem
멱등성을 보장할 외부 저장소가 없으면 같은 다이제스트가 중복 발송될 위험.
Choice
부모 메시지 텍스트에 날짜를, 스레드 reply의 fallback text에 chunk index를 박고, 발송 직전 부모 스레드의 reply를 읽어 누락 idx만 보충.
Result
DB·캐시·락 없이 멱등성 확보. 인스턴스 재시작/중복 발사에 자연 내성.
D2LLM은 거들 뿐 — 결정적 fallback을 1급 시민으로

합성 LLM이 timeout/JSON malformed/빈 결과인 경우를 “예외”가 아닌 정상 분기로 다뤘습니다. 같은 입력에는 항상 같은 fallback 결과가 나오도록 카테고리 버킷팅과 날짜 그룹핑을 결정적으로 구현.

Problem
LLM 한 회 실패가 “오늘은 발송 없음”이 되면 신뢰가 깨짐.
Choice
Stage 1까지의 구조화 결과만으로 카테고리 정렬·그룹핑하는 deterministic composer를 별도 구현.
Result
LLM 실패율이 어떻든 “최소 뉴스레터”는 항상 도착. 운영 사고 0건.
D3"노이즈 제외"가 아니라 "긍정형 추출 기준"으로 프롬프트 재작성

초기 프롬프트는 “이런 메시지는 토픽으로 만들지 마라” 식의 부정형이었는데, LLM이 무엇이 노이즈인지 판단하기 위해 본문을 길게 인용하는 경향이 있었습니다. 의사결정·진행 변화·정보 공유·일정·요청응답의 5가지 긍정형 기준으로 다시 작성하니 출력이 단정해지고 토큰도 줄었습니다.

Problem
부정형 기준은 LLM에게 “모든 메시지를 평가”하라고 요구해 출력이 장황해짐.
Choice
5가지 긍정형 카테고리로 “이 흐름이 보이면 토픽으로 만들어라”로 전환.
Result
출력 일관성↑, 토큰↓, 환각 ↓. “조용한 채널은 조용하게” 원칙이 자연스럽게 성립.
D4실명 화이트리스트로 LLM 환각 방어

LLM이 그럴듯한 한국식 이름을 만들어내 “XX님이 결정”처럼 거짓 사실을 생성하는 사고를 차단해야 했습니다. 메신저 API에서 가져온 실재 사용자 이름과 본문에 평문으로 등장한 호칭만 화이트리스트로 두고, 그 외의 이름 패턴은 통째로 제거 후 한국어 조사 잔재까지 정리했습니다.

Problem
LLM이 만들어낸 가상의 인명이 사실처럼 보고됨.
Choice
실재 인명 화이트리스트 매칭 + 외톨이 조사 정리. 행위자 미상이면 주어를 그냥 비움.
Result
“확인 완료”, “배포 결정” 같은 행위 중심 문장으로 자연스럽게 떨어짐.
D5새 채널 자동 흡수 — 사람 개입 0

새 공개 채널이 생길 때마다 운영자가 봇을 초대해야 한다면 운영 비용이 누적됩니다. 비멤버 채널은 수집 호출이 실패한 시점에 자동으로 join 후 재시도하고, 실패 사유(권한 부족·아카이브 등)는 진단 채널로 따로 보고하도록 분리했습니다.

Problem
매주 새 채널이 생기는 환경에서 수동 초대는 누락이 잦음.
Choice
실패 → 자동 join → 재시도. 실패 사유는 별도 진단 채널로 분리.
Result
신규 채널이 다음 발사부터 자동 흡수. 운영자는 진단 채널만 확인.
D6동시성은 channel-tier에 맞춰 보수적으로

외부 API의 tier-별 분당 한도를 한 번 넘기는 순간 429 폭주로 회차 전체가 망가집니다. 메시지 history는 동시성 3 + 1.2초 간격, permalink 조회는 동시성 3 + 500ms 간격으로 명시적 limiter를 두고, 429를 받았을 때는 Retry-After 헤더를 우선 신뢰하되 없으면 attempt에 비례한 백오프로 최대 3회만 재시도하도록 정책을 통일했습니다.

Problem
200+ 채널에 무제한 Promise.all을 던지면 한도 폭주.
Choice
호출 타입별 ConcurrencyLimiter + 명시적 재시도 한도.
Result
평소 발사 시간 ~5분, 한도 폭주 사고 0건.

05신뢰성과 멱등성

매일 한 번만 발사되는 시스템이라 한 회차가 깨지면 사용자는 그 차이를 바로 느낍니다. 다음 6가지 가드를 두고 “어떻게 깨져도 다음 회차가 자연 복구”되도록 만들었습니다.

가드막는 사고설계
중첩 실행 차단 직전 발사가 진행 중인데 다음 cron이 트리거 → 같은 다이제스트 이중 발송 프로세스 메모리의 runStartedAt 플래그. 양수면 다음 발사는 즉시 스킵.
hang 자동 reset 네트워크 hang으로 플래그가 영구 잠겨 모든 후속 발사가 스킵되는 사고 runStartedAt이 30분을 넘으면 강제 reset 후 새 회차 진행.
“빈 안내” 사전 dedup 한 줄 안내가 멀티 인스턴스에서 중복 발송 cron 핸들러가 발사 전에 출력 채널 최근 메시지에서 같은 날짜 안내 존재 여부 확인.
chunk 단위 멱등 회복 본문 chunk 분할 발송 도중 throw로 죽었을 때 다음 회차가 chunk 0부터 다시 보내면 중복 부모 한 줄 메시지를 같은 날짜로 재사용하고, 각 스레드 reply의 fallback text에 {date} (idx/total)를 박음. 다음 회차는 부모 스레드의 reply를 읽어 이미 보낸 idx를 빼고 누락분만 발송.
self-feedback 차단 어제 발송한 다이제스트가 오늘 입력에 흡수되어 “봇이 봇을 요약”하는 사고 출력 채널을 수집 대상에서 명시적으로 제외. 메신저 측 봇 메시지 필터에 더해 가드 한 줄을 더 둠.
stage별 timeout LLM이 응답 없이 영원히 매달려 회차 전체가 멈춤 Stage 1 90s, Stage 2 180s — 각 단계가 자체 시계로 끊고, 실패는 다음 단계의 fallback으로 흘려보냄.
회복 모델. 가드는 “이번 회차를 어떻게든 살린다”가 아니라 “다음 회차가 자연 복구되도록 상태를 정리한다”에 가깝게 설계됨. 한 회차 누락보다 잘못된 발송이 더 큰 신뢰 사고라고 판단.

06설계로 막은 사고

출시 후 실제로 운영하며 “이건 그냥 두면 사고가 났겠다” 싶었던 케이스를 코드 리뷰·디버깅 과정에서 발견하고 본 출시에 묶어 처리했습니다.

avoided · 1

HTML 응답을 JSON으로 파싱하다 raw stacktrace가 운영 채널로 노출

외부 API 게이트웨이가 500/HTML로 떨어졌을 때 응답을 그대로 res.json()에 넣으니 SyntaxError가 발생해 진단 리포트에 raw stacktrace가 그대로 노출됨.

→ HTTP status 단계에서 먼저 끊고, body 일부를 사람이 읽을 수 있는 메시지로 변환해 throw.

avoided · 2

permalink 조회가 무제한 병렬로 던져져 한도 폭주

토픽이 폭증한 날 모든 permalink를 한 번에 Promise.all로 보내면 외부 API의 분당 한도를 단숨에 넘김.

→ 호출 tier에 맞춘 동시성 limiter(3 + 500ms gap)로 유효 RPS를 안전 마진 아래로 고정.

avoided · 3

잘못된 형식의 날짜 입력이 silently 유효 윈도우로 흘러감

JS Date의 rollover 동작 때문에 "2026-99-99" 같은 입력이 검증 없이 통과해 엉뚱한 날짜 윈도우를 만듦.

→ 정규식 + 월/일 범위 검증을 입구에 두고 잘못된 입력은 명시적으로 throw.

avoided · 4

self-feedback — 봇이 자기 발송분을 다시 요약

출력 채널도 수집 대상에 포함되어 있어 이론적으로 어제 발송분이 오늘 입력에 들어갈 수 있었음(메신저 측 봇 필터로 우회 차단되긴 함).

→ 출력 채널 자체를 collector 단계에서 명시적으로 제외. “필터로 빠지더라” 대신 “애초에 안 읽음”으로 의도를 명확히 함.

07배운 점

  • “실패하지 않는 LLM 시스템”은 없다. LLM 호출은 평균적으로 잘 동작하더라도, 매일 한 번 발사되는 시스템에서는 1년에 수십 번은 실패합니다. 결정적 fallback을 “예외 처리”가 아니라 “정상 분기”로 두지 않으면 신뢰가 깨지는 건 시간 문제.
  • 상태를 어디에 둘지가 시스템의 절반을 결정한다. 별도 DB 대신 출력 채널 자체를 SSOT로 삼은 결정이 “복구 알고리즘”의 형태를 단순화했음. 인프라 한 개를 줄이는 게 아니라, 동기화 문제 자체를 없앤 게 본질.
  • 프롬프트는 “쓰지 마라”가 아니라 “이걸 써라”로. 부정형 기준은 모델에게 평가 부담을 주고 출력이 장황해짐. 5가지 긍정형 기준으로 바꾸는 작은 리팩터로 토큰·일관성·환각이 모두 개선되는 경험.
  • 가드는 “이번 회차”가 아니라 “다음 회차”를 위해. 매일 한 번 발사되는 시스템에서는 “지금 살린다”보다 “내일 자연 복구되게 한다”가 더 안전. hang 자동 reset, chunk dedup, self-feedback 차단 모두 같은 철학.
  • 리뷰는 “지적”이 아니라 “남길지 뺄지”의 기록. 자동 리뷰 + 수동 리뷰의 16개 항목을 모두 작업 / 해명 / 의도된 동작 / 후속 PR로 분류한 표를 PR에 같이 넣으니, 리뷰어와 같은 결정 위에서 토론할 수 있었음. 의견 차이는 “남은 작업”이 아니라 “명시된 선택”이 됨.
